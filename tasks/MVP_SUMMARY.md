# MVP 完成记录

核心结论：已把原来的展示页改为可操作的模拟购物闭环，完成 tasks/todo.md 的 19 个开发任务。所有付款都是模拟操作。

主要实现：

- 授权表单覆盖全部字段，支持简单文字填写草稿、人工确认和撤销。
- “party items”生成零食和气球清单，不猜数量；用户填写各目标的预算份额并接受可能部分完成。
- 搜索淘宝、HKTV Mall、拼多多的固定目录，每次展示一个目标、一个商家的最多三条报价。
- 金额由代码以整数分计算，包含运费；奖励只改变比较成本，不降低现金支出或七天账本。
- 排名显示权重、分数和理由；同分、重复购买、偏好冲突、报价变化都会暂停等待用户。
- 报价保存商品、运费、现金、币种、付款方式、奖励条款和两个到期时间。旧报价确认不能复用。
- 模拟付款仅使用账号已有的 vault/address 引用，同一付款编号只记一次账；记账时再次检查预算和最新授权。
- SQLite 保存授权、请求、购买尝试和订单，旧账号会补齐引用。退款不恢复连续 168 小时的预算。
- 每次尝试有统一追踪编号，日志包含规则、用到的数字及理由。

冲突按最简单功能处理：

| 要求差异 | 首版实现 |
| --- | --- |
| 前文要求 LLM，后文批准确定性解析 | 使用本地规则解析，仅支持目录里的零食、气球和简单授权数字；填后仍需确认 |
| 泛化多平台购物、多个商品组合，后文限定 top 3 | 搜索多个模拟平台；一目标一商家一订单；跨目标分别下单 |
| 推荐最佳支付/完整 Stripe 接入，后文仅允许 mock card | 仅模拟 card，以已存引用调用，无真实扣款 |
| Task 8 将 per-item 写成 cash，prompt 的五步公式要求优惠前商品行总额 | per-item 看优惠前行总额；per-order、份额及滚动预算看含运费的现金 |
| 现金权重与奖励比较成本可能混淆 | 现金权重基于 cash_total；奖励折算另显示为排名加分，仅奖励开启时使用 |
| 文字填写可能提高限制、增加商家或切换自动模式 | 不自动扩大授权；提示冲突，必须人工改表单并确认 |
| one-merchant 表单允许取消勾选，但首版 top 3 范围固定 | 首版仍保持一目标一商家，界面说明此限制 |

模型限制：当前聊天没有切换模型工具，可调用模型列表未包含用户指定的 `gpt6.1-ivy`，因此不能声称本次由该模型执行。开发在当前聊天完成。

验证结果：40 条测试通过，13 个回放场景超预算计数为 0；类型检查、lint、生产构建通过。代码审查中故意反转一次限额判断，测试正确失败，随后恢复。覆盖率为语句 83.15%、分支 80.90%、函数 90.08%、行 88.42%；首次实测基线已加入 CONSTRAINTS.md 和 Vitest。

浏览器在独立测试数据库中验证了注册、账户引用、空白限额报错、空白数量/份额阻止搜索、派对清单、三条报价、人工付款后记账、340→360 重新确认与拒绝回退、410 被限额拒绝。报价变化截图见 `tasks/artifacts/mvp-price-confirm.png`。

最终生产构建再次复核：原有登录正常；自动模式遇同分停在选择弹窗，唯一最高分能完成模拟付款；累计账本支出为 120 港币，与 `/account` 一致。商家列表能连续输入逗号，320/768/1024/1440 像素宽度未见横向溢出，页面没有浏览器错误日志。预览采用独立的 `data/mvp-browser` 数据库，没有操作用户原有开发服务器的账户数据。

依赖检查：新增的直接开发依赖只有 Vitest 及其覆盖率组件；原有锁定包版本未变。npm audit 的 5 条高风险报告来自原有 eslint-config-next 的开发依赖链，没有强制降级 Next.js。Docker 镜像未实际构建。真实平台、真实支付和更广商品范围留待后续；人工验收待用户完成。
